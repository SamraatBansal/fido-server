# FIDO2/WebAuthn Relying Party Server Technical Specification

**Project:** `FIDO_29_0sdvq,lefjh3ajhghascgnhbsdhnadsasasasccdcsc`

## 1. Security Requirements

| Requirement | Testable Criteria |
| :--- | :--- |
| **Origin Verification** | The server must validate that the `origin` in the client data matches the expected Relying Party origin. Requests with mismatched origins must be rejected. |
| **Challenge Freshness** | The server must generate a unique, cryptographically random challenge for each registration and authentication ceremony. Previously used or expired challenges must be rejected. |
| **Attestation Signature Verification** | The server must cryptographically verify the attestation signature using the public key from the attestation certificate chain. Invalid signatures must result in registration failure. |
| **Credential Public Key Storage** | The server must securely store the credential public key and related metadata. At no point should any private key material be requested or stored. |
| **User Handle Management** | User handles must be opaque, non-personally identifiable, and unique per user. The server should avoid using emails or usernames as user handles. |
| **Authentication Signature Verification** | The server must verify the authenticator's signature using the previously stored public key for the given credential ID. |
| **Counter (Signature Count) Verification** | The server must check that the signature counter from the authenticator is strictly greater than the last stored counter value for that credential, to prevent cloned authenticators and replay attacks. |
| **TLS Enforcement** | All communication between the client and the server must be over a secure TLS connection. The server should reject any non-TLS requests. |

## 2. Technical Scope

### 2.1. Registration (Attestation)

*   **Success Conditions:**
    *   A unique challenge is generated and sent to the client.
    *   The client's response is successfully parsed and validated.
    *   Attestation signature is verified.
    *   The new public key credential is created and associated with a user.
    *   The signature counter is initialized and stored.
*   **Failure Conditions:**
    *   Invalid or expired challenge.
    *   Mismatched origin.
    *   Invalid attestation format or signature.
    *   User handle already exists for another user.
    *   Credential ID already registered.

### 2.2. Authentication (Assertion)

*   **Success Conditions:**
    *   A unique challenge is generated and sent to the client.
    *   The client's response is successfully parsed and validated.
    *   The authenticator's signature is verified against the stored public key.
    *   The signature counter is greater than the stored value.
    *   A new session is established for the authenticated user.
*   **Failure Conditions:**
    *   Invalid or expired challenge.
    *   Mismatched origin.
    *   Unknown credential ID.
    *   Invalid signature.
    *   Stale or decremented signature counter.

## 3. Rust Architecture (`webauthn-rs`)

A recommended project structure to facilitate testing and maintainability:

```
.
├── Cargo.toml
├── tests/
│   ├── api/
│   │   ├── registration.rs
│   │   └── authentication.rs
│   └── compliance.rs
└── src/
    ├── main.rs         // Application entry point, server setup
    ├── lib.rs          // Library crate root
    ├── api/
    │   ├── mod.rs
    │   ├── registration.rs // Registration handlers
    │   └── authentication.rs // Authentication handlers
    ├── models.rs       // Data structures (User, Credential)
    ├── db.rs           // Database interaction logic
    └── config.rs       // Application configuration
```

*   **Testing:**
    *   **Unit Tests:** Reside within each module (`#[cfg(test)]`). Focus on testing individual functions, such as data validation and cryptographic operations.
    *   **Integration Tests:** Reside in the `tests/` directory. These will test the API endpoints by making HTTP requests to a running instance of the server.
    *   **`webauthn-rs` Integration:** The `webauthn-rs` library will be the core component for handling the FIDO2 logic. Your handlers in `api/` will orchestrate the calls to `webauthn-rs` and your database layer.

## 4. API Design (REST)

### Registration

**1. `POST /register/start`** (Initiate Registration)

*   **Request Body:**
    ```json
    {
      "username": "someuser",
      "displayName": "Some User"
    }
    ```
*   **Success Response (200 OK):**
    ```json
    {
      "publicKeyCredentialCreationOptions": {
        // As generated by webauthn-rs Passkey::begin_registration()
      }
    }
    ```

**2. `POST /register/finish`** (Complete Registration)

*   **Request Body:**
    ```json
    {
      "publicKeyCredential": {
        // The full object from the client's navigator.credentials.create() call
      }
    }
    ```
*   **Success Response (200 OK):**
    ```json
    {
      "status": "ok",
      "verified": true
    }
    ```
*   **Error Response (400 Bad Request):**
    ```json
    {
      "status": "failed",
      "message": "Detailed error message"
    }
    ```

### Authentication

**1. `POST /authenticate/start`** (Initiate Authentication)

*   **Request Body:**
    ```json
    {
      "username": "someuser" // Optional, if you allow user-identifying authentication
    }
    ```
*   **Success Response (200 OK):**
    ```json
    {
      "publicKeyCredentialRequestOptions": {
        // As generated by webauthn-rs Passkey::begin_authentication()
      }
    }
    ```

**2. `POST /authenticate/finish`** (Complete Authentication)

*   **Request Body:**
    ```json
    {
      "publicKeyCredential": {
        // The full object from the client's navigator.credentials.get() call
      }
    }
    ```
*   **Success Response (200 OK):**
    ```json
    {
      "status": "ok",
      "verified": true
    }
    ```
*   **Error Response (400 Bad Request):**

## 5. Storage Requirements

### User Table (`users`)

| Column | Type | Constraints | Notes |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | Primary Key | Unique user identifier. |
| `username` | `TEXT` | Unique, Not Null | User's unique username. |
| `display_name` | `TEXT` | Not Null | User's display name. |

### Credentials Table (`credentials`)

| Column | Type | Constraints | Notes |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | Primary Key | |
| `user_id` | `UUID` | Foreign Key (`users.id`) | Links credential to a user. |
| `credential_id` | `BYTEA` | Unique, Not Null | The `credentialId` from the authenticator. Stored as raw bytes. |
| `public_key` | `BYTEA` | Not Null | The COSE public key. |
| `sign_count` | `BIGINT` | Not Null | The signature counter. |
| `transports` | `TEXT[]` | | Authenticator transports (e.g., "usb", "nfc", "ble"). |

**Data Validation:** All incoming data must be validated before database insertion. The `credential_id` and `public_key` should be handled as raw binary data.

## 6. Compliance Checklist

This checklist provides a set of testable compliance points.

| # | Specification Point | Test Case |
| - | :--- | :--- |
| 1 | **RP ID Hashing:** The `rpId` is correctly hashed in `clientDataJSON`. | Test that `hash(rpId)` matches `clientData.rpIdHash`. |
| 2 | **Challenge Validation:** The server must validate the challenge from the client. | Send a modified/invalid challenge in the client response and assert failure. |
| 3 | **Origin Validation:** The server must validate the origin from the client. | Send a request with a mismatched origin and assert failure. |
| 4 | **Token Binding:** (If used) The server validates token binding information. | Test with and without token binding headers. |
| 5 | **Attestation Verification:** Correctly verify different attestation formats (`packed`, `fido-u2f`, etc.).| Create tests for each supported attestation format. |
| 6 | **UP/UV Flags:** The server correctly checks the `userPresent` (UP) and `userVerified` (UV) flags. | Test registration/authentication with different authenticator settings for UP/UV. |
| 7. | **Signature Counter:** The server correctly implements signature counter checks. | Send an authentication response with a stale or decremented counter and assert failure. |
| 8. | **AllowCredentials List:** The server correctly builds the `allowCredentials` list for authentication. | Check that the list is correctly populated for a given user. |

## 7. Risk Assessment

| Risk | Threat | Mitigation Strategy |
| :--- | :--- | :--- |
| **Replay Attacks** | An attacker captures a valid authentication assertion and replays it to gain unauthorized access. | **Challenge-Response:** Use a unique, single-use challenge for every authentication ceremony. **Signature Counter:** Strictly enforce that the signature counter increases with each authentication. |
| **Credential Theft (Server-side)** | An attacker gains access to the Relying Party's database. | **Store Only Public Keys:** Never store any private key material. The credential public keys are public information. **Data Minimization:** Do not store any unnecessary user information. |
| **Phishing** | A user is tricked into authenticating on a malicious website. | **Origin Binding:** The FIDO2 protocol inherently mitigates this by binding credentials to a specific origin. Your server *must* strictly enforce this origin check. |
| **Cross-Site Request Forgery (CSRF)** | An attacker forces a logged-in user to perform an unwanted action. | Use standard CSRF protection mechanisms on all state-changing endpoints that are not part of the FIDO2 ceremony (e.g., associating a new credential to a logged-in account). |
| **Authenticator Cloning** | An attacker creates a copy of a user's authenticator. | **Signature Counter:** This is the primary defense. If the counter does not strictly increment, the server must reject the authentication. |

This specification provides a solid foundation for building and testing your FIDO2/WebAuthn Relying Party server. By following these guidelines, you can ensure a secure and compliant implementation.
